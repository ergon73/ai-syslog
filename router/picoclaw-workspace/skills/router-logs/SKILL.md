# Skill: Анализ логов роутера

Используй этот навык, когда владелец спрашивает про события, лог, безопасность,
устройства, интернет, VPN или «что происходило».

## Порядок действий

1. «Что было за сутки / важные события» → читай /opt/etc/observer/state/day.acc
   (агрегат: ЧИСЛО_ПОВТОРОВ <TAB> ПРОГРАММА <TAB> СООБЩЕНИЕ). Отсортируй в уме
   по важности, а не по числу повторов: 5 неудачных логинов важнее 5000 строк
   шторма WireGuard.
   ВАЖНО про период: day.acc очищается каждый день в 08:00 (после утреннего
   дайджеста) и копится заново. Утром в нём данные только за пару часов!
   Предыдущие сутки лежат в day.acc.prev — для полной картины «за сутки»
   читай ОБА файла и честно называй охваченный период.
2. «Что происходит прямо сейчас» → читай хвост /opt/var/log/router.log
   (например, последние 200-400 строк). Формат:
   UNIXTIME <TAB> LEVEL <TAB> HOST <TAB> PROGRAM <TAB> MSG.
   UNIXTIME переводи в человеческое время (часовой пояс владельца MSK, UTC+3).
3. «Почему пришло уведомление» → /opt/etc/observer/state/interesting
   (последний батч незнакомых событий) и /opt/etc/observer/state/batch.txt.
4. Статистику работы наблюдателя бери из /opt/etc/observer/state/stats
   (lines=строк за сутки, kept=после фильтра, llm=вызовов LLM, tg=уведомлений).

## Интерпретация

- Списки известного шума: /opt/etc/observer/drop_patterns.txt (отброшено до
  анализа) и /opt/etc/observer/boring_patterns.txt (не тревожим владельца,
  но видно в day.acc). Событие из этих списков упоминай только как тренд.
- Сигналы безопасности: "MIC differs in key handshaking" — неверный пароль
  Wi-Fi; dropbear "exit before auth"/"bad password" — попытки SSH;
  "authentication failed" — вход в веб-интерфейс.
- Новые устройства видны по DHCPREQUEST с незнакомым hostname.
- В day.acc адреса ЗАМАСКИРОВАНЫ (MAC/IP/N) — это нормально. В сыром
  router.log MAC/hostname в открытом виде.
- ОБЯЗАТЕЛЬНО для ЛЮБОГО события безопасности (MIC differs, попытки входа,
  подозрительная активность): ПРЕЖДЕ чем судить «свой/чужой» или «атака»,
  сопоставь MAC с известными устройствами — найди по этому MAC строку
  DHCP с hostname в router.log (loggrep по MAC). Устройство, у которого
  есть hostname и штатная аренда IP — СВОЁ, не «чужое» и не атака, даже
  если MAC выглядит «случайным» (это может быть рандомизация MAC у
  телефона). «Чужим»/подозрительным называй ТОЛЬКО MAC без hostname и
  без нормальной аренды. Никогда не пугай владельца «атакой», не проверив.
  ВАЖНО: для опознания ищи MAC за ДЛИННОЕ окно (loggrep этот_MAC, hours=168):
  hostname устройства мог появиться в DHCP давно и не попасть в 24-часовое
  окно. «Не нашёл hostname за сутки» ≠ «неизвестное устройство» — расширь
  поиск, прежде чем называть MAC чужим.

## Поиск по логу — loggrep (ГЛАВНЫЙ инструмент для «найди событие X»)

Не листай большой лог кусками вслепую (чтение режется по ~64 КБ — будут
дыры в покрытии). Вместо этого используй поиск через демона:

1. Запиши write_file файл `requests/loggrep.req` (относительно workspace):
   - строка 1: искомая ПОДСТРОКА, точно как в логе (не regex!),
     например: MIC differs
   - строка 2 (необязательно): hours=48   (за сколько часов искать, до 168;
     без неё — за 24 часа)
2. Демон выполнит поиск за ~2 секунды. Сделай следующим вызовом read_file
   `results/loggrep.txt` — в шапке будет ТВОЙ запрос и время; если там ещё
   старый поиск — прочитай файл повторно (пара секунд уже пройдёт).
3. Результат — до 200 последних совпавших строк; КАЖДАЯ начинается с
   готового местного времени "YYYY-MM-DD HH:MM | ..." (MSK). Используй
   ЭТО время как есть. Unixtime из строки НЕ конвертируй сам — ты в этом
   систематически ошибаешься; готовое время всегда приоритетнее твоих
   вычислений.
4. Для вопросов «СКОЛЬКО раз/устройств/событий»: в шапке результата есть
   строка "# ВСЕГО СОВПАДЕНИЙ: N" — точное число по всему периоду.
   НЕ считай строки сам (их максимум 200, при больших объёмах будет
   недосчёт). Для «сколько РАЗНЫХ устройств» — совпадений может быть
   больше, чем устройств: собери уникальные MAC/hostname из строк,
   а если строк ровно 200 (обрезка) — честно скажи, что счёт уникальных
   неполный, и назови число по видимой части с оговоркой.

## Время и unixtime (КРИТИЧНО — здесь уже были ошибки)

- Текущий unixtime НЕ вычисляй в уме — возьми якорь из
  /opt/etc/observer/state/metrics.now: строка "unixtime_now=..."
  (обновляется каждые 5 минут; там же в шапке дата уже в MSK).
- Возраст события = unixtime_now − ts (секунд). Для абсолютного времени:
  unixtime → UTC, затем ПРИБАВЬ 3 часа (MSK=UTC+3). Частая ошибка — назвать
  UTC-время «MSK», не прибавив 3 часа. Проверь себя возрастом события.
- РАЗОБРАННЫЙ ПРИМЕР: unixtime_now=1783749119 — это 11.07 08:51 MSK.
  Событие ts=1783722436: возраст = 26683 с ≈ 7,4 часа → 08:51 − 7,4 ч ≈
  01:27 MSK этой ночью. Считай именно так, через возраст.
- Вопрос про период («этой ночью», «за час», «сегодня») — СНАЧАЛА вычисли
  границы периода в unixtime, потом отбирай ТОЛЬКО события с ts внутри.
  Событие вне периода НЕ подгоняй под вопрос, каким бы похожим оно ни было.
- Если в спрошенном периоде событий нет — так и скажи. Прежде чем назвать
  время события, проверь себя: возраст события согласуется с периодом вопроса?

## Правила чтения больших файлов (КРИТИЧНО — здесь уже были ошибки)

- router.log растёт примерно на 1 МБ в сутки (~50 КБ в час). Сколько читать —
  считай ОТ ПЕРИОДА вопроса: offset = total − (часов_периода × 50000), с
  запасом ×2. «Этой ночью» (8-10 часов назад) = минимум последние ~500 КБ;
  просто «хвост» в 100 КБ покрывает лишь ~2 часа!
- ПРОВЕРКА ПОКРЫТИЯ: ts первой строки прочитанного куска должен быть МЕНЬШЕ
  unixtime начала спрошенного периода. Если нет — период не покрыт, читай
  дальше назад (уменьшай offset). Без этой проверки ответ невалиден.
- Если ответ инструмента содержит "TRUNCATED" — ты ОБЯЗАН дочитать файл
  следующими вызовами read_file с указанным offset, до самого конца.
- ЗАПРЕЩЕНО утверждать «событий не было», пока не покрыт весь период,
  о котором спрашивает владелец. Не покрыл период = не проверил.

## Ограничения

- Только чтение перечисленных файлов. Никаких команд управления роутером.
- Если данных не хватает — так и скажи, не выдумывай.
- В ответе не показывай сырые строки лога без необходимости — владельцу
  нужен вывод, а строки цитируй выборочно как доказательство.
